# Operations

Day-to-day operation of a hermes-orchestrator stack: health, backups, updates, retention, caches, configuration drift, and pinned versions. Recovery after failures is in [recovery.md](recovery.md); Hermes channels and approvers in [hermes.md](hermes.md); the security tests in [security-tests.md](security-tests.md).

`ho` is `docker compose exec control-plane ho`. All scripts accept `HO_COMPOSE_PROJECT` (default `hermes-orchestrator`) and `HO_ENV_FILE` (default `.env`).

## Health

```bash
make check                 # control plane ready, dependencies healthy, schema at head, Hermes plugin and Dashboard up
ho recovery status         # component health (DEGRADED after three failed probes), open intents, pending notifications
ho health                  # control plane readiness
```

`GET /metrics` (operator token) serves Prometheus text: tasks by state, queue length, executions, provider tokens, approvals, notifications, and component health. Nothing in v1 requires Prometheus; point a scraper at it if you run one.

## Backups

`make backup` (or `scripts/backup.sh`) writes `backups/<UTC timestamp>/`:

| File | Content |
| --- | --- |
| `postgres.dump` | the whole platform database (`pg_dump --format=custom`) |
| `hermes-data.tar.gz` | Hermes's state: SQLite databases copied with SQLite's online backup API, skills, memories, configuration with secret values removed |
| `artifacts.tar.gz` | execution evidence (skip with `HO_BACKUP_ARTIFACTS=0`) |
| `config/`, `env.settings` | platform configuration; `.env` without values whose names contain TOKEN, PASSWORD, SECRET, or KEY |
| `MANIFEST.json`, `SHA256SUMS` | Git commit, `HO_VERSION`, schema revision; checksums verified on restore |

Never included: `./secrets`, provider logins (`cred-*` volumes), the GitHub login (`gh-config`), Redis, workers, test environments. Projects live in Git. The newest `HO_BACKUP_KEEP` backups (14) are kept.

Daily schedule:

```bash
# macOS (launchd): ~/Library/LaunchAgents/dev.hermes-orchestrator.backup.plist runs every day at 03:00
cat > ~/Library/LaunchAgents/dev.hermes-orchestrator.backup.plist <<EOF
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>dev.hermes-orchestrator.backup</string>
  <key>ProgramArguments</key><array><string>/bin/bash</string><string>-lc</string>
    <string>cd "$PWD" && scripts/backup.sh >> backups/backup.log 2>&1</string></array>
  <key>StartCalendarInterval</key><dict><key>Hour</key><integer>3</integer><key>Minute</key><integer>0</integer></dict>
</dict></plist>
EOF
launchctl load ~/Library/LaunchAgents/dev.hermes-orchestrator.backup.plist

# Linux (cron)
( crontab -l 2>/dev/null; echo "0 3 * * * cd $PWD && scripts/backup.sh >> backups/backup.log 2>&1" ) | crontab -
```

Restore (stops the services that change state, restores PostgreSQL in place, Hermes's state, and artifacts, starts the stack, re-applies secrets through `hermes-init`, and lets the startup reconciliation align executions and workspaces):

```bash
make restore BACKUP=backups/20261001T030000Z
make check
```

After restoring onto a new machine, log in to the providers again (`make auth-claude`, `make auth-codex`, optionally `make auth-github`).

## Updates

Updates follow snapshot → update → health check → rollback on failure, and need an approval:

```bash
git pull                                   # the new platform version (or check out a tag)
scripts/update.sh 1.1.0                    # requests the UPDATE approval (bound to the running version)
ho approval approve <approval-id>          # or /orch approve <id>, or the Dashboard
scripts/update.sh 1.1.0 <approval-id>
ho update list                             # STARTED, SUCCEEDED, ROLLED_BACK, or FAILED, with the backup used
```

`update.sh` consumes the approval (refused if it is not approved, expired, or the running version changed), takes a backup, builds the images with the new tag, starts the stack (migrations run first), and runs `scripts/check.sh`. If the check fails it runs `scripts/rollback.sh`: the previous version's images (still tagged) and the pre-update backup (migrations only move forward). To roll back by hand later: `HO_ROLLBACK_VERSION=<version> scripts/rollback.sh backups/<timestamp>`.

## Pinned versions

| Component | Where |
| --- | --- |
| Base images (Python, Debian, Node, Playwright, PostgreSQL, Redis) | Dockerfiles and `compose.yaml`, by multi-architecture index digest |
| Hermes | `compose.yaml`, `nousresearch/hermes-agent@sha256:fca358f1…` (v0.21.5) |
| Claude Code, Codex CLI, Flutter | `workers/versions.env` |
| Python dependencies | `requirements.lock` |
| Execution images allowed to run | `config/images.lock.yaml` (generated by `make images`; Agent Manager refuses anything else) |

Changing a pinned version is an update: rebuild, run the tests and smoke tests, then update through the approval above.

## Architectures

The stack runs on Apple Silicon (ARM64) and x86-64 or ARM64 Linux. Every base image is pinned to a multi-architecture index. `scripts/check-multiarch.sh` builds all images for the other architecture and runs each under emulation (`HO_CHECK_PLATFORM=linux/arm64` on an x86-64 host). Machine profiles are separate: `config/mac-m2-pro.yaml` and `config/linux.yaml`, selected with `HO_MACHINE_PROFILE`.

## Retention and cleanup

Run daily by the scheduler (`ho maintenance run` on demand):

| What | Rule | Setting |
| --- | --- | --- |
| Workers and test environments | removed as soon as an execution or task ends | — |
| Workspaces of merged tasks | removed after the merge | — |
| Workspaces of cancelled or failed tasks | kept (commits collected), removed after N days | project `retention.failed_workspace_days` (14) |
| Execution outputs and logs | files removed after N days; metadata and digests kept | project `retention.artifacts_days` (30); `platform.retention.failed_artifacts_days` (90) for failed or blocked tasks |
| Requests, requirements, plans, onboarding reports, manifests | kept | — |
| Delivered notifications, recovery reports | pruned | `platform.retention.notifications_days`, `recovery_runs_days` (30) |
| Task history in PostgreSQL | kept | — |
| Backups | newest N kept | `HO_BACKUP_KEEP` (14) |

## Dependency caches

Executions that write a workspace get package-manager download caches per project and ecosystem (`ho-cache-<project>-pip|npm|gradle|pub|composer`), never shared between projects; `node_modules`, virtualenvs, and build outputs stay in the workspace. The daily maintenance trims each cache to `machine.dependency_cache.max_gb_per_cache` (2 GB by default), least recently used files first, never while a worker uses it.

```bash
ho cache list                              # size and use of each cache
ho cache clear my-app --ecosystem npm      # invalidate one (or all of a project's caches without --ecosystem)
```

## Configuration drift and sensitive changes

Every task pins the project configuration it started with. A rescan (`ho project scan`) compares the repository's `.hermes/project.yaml` with the active configuration; a difference records `CONFIG_DRIFT_DETECTED`, puts the project in `DRIFT_DETECTED` (no new planning), and proposes the new configuration, which takes effect only through a new `PROJECT_READY` approval. Running tasks keep the configuration they pinned. No project configuration can relax the platform's hard policies (protected branches, worker isolation, secrets by reference, production off by default).

Platform-level changes (machine profile, approvers, policy) are files in `config/` and `.env`, versioned with the repository and applied by `make up`; updates of the platform itself go through the UPDATE approval.
