# Pinned worker-image recovery

T-10 failed before planning because both pinned Odoo provider images were absent. Three requests
used launch budget and caused provider failover despite no worker starting. This change separates
image readiness, permanent policy rejection, and actual agent execution.

## Behavior

- Verify the worker and required helper images before reserving a launch.
- Restore missing allowed images from an operator-built local archive, asynchronously and without
  registry/tag fallback. Verify the exact pinned image and platform label before use.
- Keep orchestration launches queued while restoring; resume automatically on the normal scheduler pass.
- Retain one execution if its image disappears between preflight and dispatch, with a bounded wait.
- Refund definitively refused, unstarted launches; retain charges for ambiguous remote errors.
- Report permanent policy rejection and failed recovery with the actual cause, without provider cycling.
- Save the compressed local recovery archive on image builds; exclude it from Git, build contexts, and critical-state backups.

No schema migration, provider credential change, approval bypass, or Odoo module change is required.
The local archive must first be generated by a successful `make images`. Missing or corrupt archives
produce an actionable wait instead of arbitrary worker rebuilding. Existing historical launch charges
are not rewritten retroactively.

and proxy image IDs are now present, and the local compressed archive occupies approximately 4.31 GiB.
T-10 was explicitly retried after checking that it was still blocked by the original missing-image
failures; its Claude orchestrator worker then reached RUNNING and SUCCEEDED. Requirements and plan version 1
were accepted, followed by a Claude DEVELOPER execution observed RUNNING without a failure reason.
